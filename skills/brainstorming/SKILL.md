# Brainstorming

あなたは構築がとても得意です。人間パートナーが望んでいると思うものを構築しますが、その信じ込みは実際より薄っぺらいのが普通です。このスキルは、何かが作られる前に、相手が実際に何を望むのか、なぜ望むのかを見つけ出すためのものです。

人は自分の望むものをまだ考え切れていないことがあります。良い質問は、考えを整える助けになります。なぜなら、その「なぜ」を理解していれば、相手が口にしない無数の決定を、相手ならそう下したであろう仕方で下せるからです。

## まず: 自分は実際に何を知っているか？

返信する前に自問してください: 相手が何を望み、なぜ望むのかについて、私は何を知っているか？

- **重要なことはすべて要求の中にある**（「アイコンを矢車菊色にして」）。これは素早く明確なタスクです。それを実行し、何をしたか伝えます。
- **些細ではない欠落がある。** 対話を始めます。

実装に着手する前に、必ず順番に次のステップを踏みます:

1. 構築の手法（approaches）を独立した1メッセージで並べ、人間パートナーに1つ選んでもらいます（「手法の提示」を参照）。
2. デザイン文書を書きます — 短いものまたは完全なもの（「作業の規模を決める」を参照）。
3. その文書の承認を得ます。
4. superpowers:writing-plans スキルを起動します。

実装ではないものが2つあります: 相手が Yes と言ったスパイク（「感覚をつかむためのスパイク」を参照）、および質問を省略して良いと選択された後で相手の要求どおりに作業することです。

## 聞く前に見る (Look Before You Ask)

既存のプロジェクトを扱うとき、または相手が文脈を与えてくれたとき（仕様、計画、引き継ぎ、指し示されたファイル、以前の会話）は、最初のメッセージの前に掘り込みます。相手が参照したもの、およびそれがつながるコードや資料を読み、関係する部分がどのように今動いているか、この変更がどこに触れるかを説明できるようになるまで読み続けます。プロジェクトや相手の文脈が既に答えていることは、決して尋ねません。

## 最初のメッセージ

次のいずれかで、作業を前に進めます:

- **相手が既に望むものを述べている**（仕様、計画、詳しい要求）: メッセージ全体で約200語を目指します。相手の要求を自分の言葉で言い返します — 相手がその骨格を見て「取れているか」を確認できるように: 相手の欲しいもの、誰のためのもの、そしてなぜを、相手が述べた範囲で。それに影響する見つけた内容を加えます: 関係する部分がどのように今動いているか、この変更がどこに触れるか。相手が考え切れていないであろうことで、相手が欲しいものやその作り方を変えるもの — 制約、衝突、より安い経路など — は、率直にそのまま述べます。どう作るかは後で決めます: 相手の望みを理解してから（「手法の提示」を参照）。メッセージは、訂正を促す1行、そして相手の望みについての質問1つで締めます: 相手の要求が開けている点のうち、その答えが作られるものを最も変えるもの。仕様はしばしば不完全なので、その上に作る前に確認します。
- **まだ述べていない:** 相手の要求が最も定めていない最大の点について、開かれた質問を1つ、相手自身の言葉で。なぜ尋ねるかも述べます: その答えが、あなたが作るものの何を変えるか。「うちのパン屋のためのウェブサイト」なら: 「主に立ち寄るかどうか迷う人向けなら、営業時間と今日の品出しを先に出します。注文を受け付けるのは別のサイトです。訪れた人に何をしてほしいですか？」

メッセージの締め方は、相手のメッセージがブレインストーミングを求めているかどうかで決まります:

- **求めている**（名前を挙げて、起動して、またはデザインの議論を求めている）: 質問で締めます。相手はこの対話を求めています。
- **求めていない:** 対話すら望まないかもしれません。質問の後に、むしろ一気に始めても構わないという軽い1行の申し出を添えます: 「あるいは私が一気に着手してよければ、そう言ってください。」 相手がそれを受け取ったら、このスキルは完了です: どう作るかにまつわる重要な選択（プラットフォーム、言語、媒体）を1行の平易な文章で述べ、普通のワークフローで相手の要求どおりに進めます。

以上だけがメッセージです。

## 対話

各メッセージは1つの質問で終わります: 例示の選択肢リストを吊るしていない1文です。平易な言葉を使い、人間パートナーより少しだけ上の水準に合わせます。相手の語彙に合わせ、過程用語（プロセス用語）は決して使わないでください。このスキルを人間パートナーに引用する必要は決してありません。

明確かつ簡潔に。重要なことから始めます。専門用語（ジョーゴン）は避けます。見つけたことを伝えるときは、最も重要な発見を先に示し、残りを提供します。

**相手に語ってもらう。** 開かれた質問が先です。相手自身の言葉には、あなたの選択肢では運べない意図が載っています。選択肢の短いメニューを出すのは、相手が詰まっているときだけです。「当てで言って」「あなたはどう思う？」と言われたら、具体的な案を提示します。

**どう作るか。** あらゆるプロジェクトは、媒体・道具・材料・リソースの選択の上に成り立っています: アプリならプラットフォーム、プログラミング言語、ライブラリ。芸術作品なら媒体。それらの選択を、どれを相手が決めたいのか、どれをあなたに任せるのか、相手が今どのような資産で作業できるのか、早めに把握します。強い意見や技能を持つ人は、話し合ったがるでしょう。あなたに委ねようとする人は、平易な言葉で言われたまっとうなデフォルトを必要とします。既存の作業があるときは、そこで既に使われているものの上に構築します。あなたが決めた選択は、その都度あなたの判断としてデザインに記します。絶対に、相手が同意したかのように書かないでください。

**覆うべき地盤。** これは地図であり、台本ではありません。次の事柄を読み上げる質問としては決して使わないでください:

- それがどういう種類のものか、何がそれを特別にするか
- なぜ今なのか、成功が相手にとってどう見えるか
- ゴール、非ゴール、アンチゴール（技術的には動いてもこれは失敗、というもの）
- 先行事例: 他で見たものの中で、気に入ったものと嫌いだったもの
- 現在の状態: 今存在するもの、相手が試したことのあるもの
- 相手が気にしている細部

**すべての質問を具体的に作る** — 相手のプロジェクトと、相手が語ってくれたことに合わせます。鋭い同僚のようにソクラテス的に尋ねます: 各質問を相手の直近の答え、または自分が見つけたものの上に組み上げ、相手がその帰結や見逃しがちなケースを考え抜けるようにします（「投票は会議の前に締め切られ、今月2人が新たに参加しました。途中から参加した人に投票権はありますか？」）。理由が明らかでないときは、何を知りたいか、またはその答えが何を変えるかを述べます。修正してもらえる提案を、その理由とともに出す方が、しばしば質問に勝ります。

**調査の申し出。** ある程度の地盤が得られ、さらに調べることが助けになりそうなときは、見に行くことを申し出ます: 相手のコードベースやプロジェクトのさらに奥、相手自身のファイルとデータ、あるいはウェブ。何を探すかも伝えます。行くかどうかは相手が決めます。

**手法の提示。** 相手の望みを理解できたら、何かを書き上げる前に、構築する道筋を独立した1メッセージとして並べます。いくつかの実際的な代替案を出し、弱いものを捨てます — 相手が望む「なぜ」に反するもの、既存の作業が排除するものも捨てます。残った2〜3案を、プロジェクトが実際に何をしているかに錨を下ろし、それぞれが何をトレードオフするかを述べて提示します。1案を推薦しその理由を述べ、どの道に進みたいかを尋ねます。適切な道が実は1つしかないときは、その旨と、他の案がなぜ合わないかを説明します。これは「どう作るか」についての話です。相手が「何を望むか」の話は、まず相手に語ってもらいます。

**語らず、見せる。** 見ることが読むより役立つ場面では、常にビジュアル・コンパニオン（下記）を申し出ます:

- 相手が目にするもの: 画面、ページ、プリント、看板
- レイアウトや割り付け: 画面、部屋、スケジュール
- フローや手順の並び
- 見た目が互いに異なる選択肢
- 図、タイムライン、マップなど、読むより見たほうが分かる構造

受け入れられた後は、反応を受け取るためのモックアップ、並べた選択肢、クリックできる使い捨てプロトタイプに使います。

**感覚をつかむためのスパイク。** エージェント的な作業はウォーターフォールですが、ひどく速いのです。使い捨ての素早い構築は、相手が何を望むのか、あるいは何かが動くのかを学ぶ最も安い手段であることが多い。助けになるなら申し出ます。相手がただスパイクを望むなら、道を開けます。スパイクにはテストを付けないか最小限に留め、頑健に作らず、計画・実装・レビューのプロセスを省きます。スパイクが教えたことは対話に持ち帰ります。

## 理解を再生して返す

進みながら再生します。ある部分を説明できるくらい理解できた時点で（それが何のためのものか誰のためのものか、あるいは一つの部品がどう振る舞うかなど）、その部分を200〜300語程度で文章にして返し、次の部分についての質問に戻ります。再生と質問は対話全体を通して交互に繰り返し、最後のまとまりで残りをすべてカバーします。

相手の言葉だけが「相手のもの」として入ります。あなたが補ったものは、その理由付きのあなたの提案として入ります。各まとまりは「何が間違っているか、欠けているか」を聞く質問で締めます。

まとまりを送る前に確認します: それは画面・ページ・スケジュール・プリントのように相手が目にするものの説明ですか？ その場合、まだビジュアル・コンパニオンの申し出をしていなければ、その申し出（下記の独立メッセージ）を代わりに送り、そのまとまりは次のメッセージまで取っておきます。受け入れられた後は、モックアップを説明の隣に置きます。

## 作業の規模を決める

相手の望みを理解でき、相手が手法を選んだら、作業がどれだけ大きいかを平易な言葉で声に出します。相手はそれを上書きできます。

| 規模 | デザイン文書 |
|------|--------------|
| 小さな変更 | 短いもの: 既に一緒にカバーした内容を書き留めたもの |
| プロジェクト | 完全な書かれたデザイン（下記） |

短いか完全かにかかわらず、デザイン文書には **手法 (Approaches)** の部分を含めます: 検討した構築方法の2〜3案、それぞれが何をトレードオフするか、相手が選んだ案とその理由。相手が選ぶのは文書を書く前、対話の中でのことです。

タスクの途中で規模が大きくなったら、停止し、その旨を述べ、1つ上の規模へ切り上げます。

本当に複数の独立したプロジェクトなら、そう言って順序を合意し、一つずつブレインストーミングします。

## 書かれたデザイン

その分野の有能な構築者が人間パートナーに立ち戻ることなく計画を立てられる、飾らない文書を書きます。次をカバーします:

- 意図とそのなぜ
- ゴール、非ゴール、アンチゴール
- 制約
- 手法（前述）
- 「どう作るか」のうち相手が決めた部分、相手が決めた通りに
- 構築者に残された部分

小さな変更の場合、短いデザインは同じ各点を1〜2行ずつでカバーし、ビルダーチェックなしで、直接人間パートナーに渡します。

**保存先:** ソフトウェアリポジトリでは `docs/plans/YYYY-MM-DD-<topic>-design.md` に書いてコミットします。それ以外の場合は尋ねます。人間パートナーの希望が常に両者を上書きします。

**ビルダーチェック（プロジェクトの場合）:** このディレクトリの `builder-check-prompt.md` を持つ新しいサブエージェントを派遣します。文書を書き上げると人間パートナーに伝える際は、先にレビュアーがそれを読み、いくつかの質問を持って1度だけ差し戻すことがある旨を伝えます。チェックが返ってくるまで文書を渡しません。ビルダーが出した質問を3つの山に分けます:

- **既に回答済み** — 対話かプロジェクトで答えがあるもの: その答えを文書に入れます。
- **些細なもの** — まっとうなビルダーなら、作るものを変えずに決められるもの: 自分で決め、文書内にあなたの判断だと印を付けます。
- **相手のもの** — 人間パートナーにしか答えられず、答えが作るものを変えるもの。

「相手のもの」の山は1つのメッセージで、重要な順に持ち込みます。回答を文書に反映し、それから精査しやすいようあなたが下した判断の短いリストを添えて文書を渡します。これがチェックが生む唯一の質問ラウンドです。サブエージェントツールがない場合は、自らがそのビルダーとして文書を読みます。

<HARD-GATE>
あなたの人間パートナーがデザイン文書を承認するまで、何も構築しません: 小さな変更なら短い文書、プロジェクトなら完全な文書。構築には、製品コードの記述、雛形の作成、依存関係のインストール、プロジェクトの作成、実装スキルの起動を含みます。読むことと探索は構いません。

2つの例外があります。質問を省略するよう選ばれた場合は、このスキルもゲートもそこで役目を終えます。相手が Yes と言ったスパイクは構築して構いません。ただし破棄物としてのラベルが保たれ、その成果物を残すことは新しい要求であり、このゲートを再び通ります。

デザイン文書が承認された後の次の一歩は計画です: superpowers:writing-plans を起動し、他のスキルは何も起動しません。
</HARD-GATE>

## Red Flags

| 思考 | 現実 |
|---------|---------|
| 「相手が欲しそうなもののメニューを出そう」 | 選択肢は誘導する。まず相手に語らせる。 |
| 「まっとうなデフォルトを当てはめよう」 | 良い。ただし声に出して言うこと。しかし聞いたことのないデフォルトは拒否できないデフォルトだ。 |
| 「質問には答えた、だから文書を書こう」 | 先に手法を並べること。相手宛ての独立したメッセージで。 |
| 「先にプロセスを説明すべきだ」 | 質問を投げること。プロセスはそのうち自ずと見えてくる。 |
| 「アイデアに "sounds good" と言われた」 | 承認は見せたものにのみ及ぶ。まだ書いていないデザイン文書は承認されていない。 |
| 「スパイクは動いた、これを土台に作り続ける」 | 残すことは新しい要求。ゲートへ戻る。 |

## ビジュアル・コンパニオン

モックアップ、図、プロトタイプを表示するためのブラウザタブ。これは道具でありモードではありません: 受け入れても、すべての質問がブラウザに送られるわけではありません。

**申し出はジャストインタイムに。** 上の場面のうちどれかが最初に出てきたときに申し出ます。事前には決して申し出ないでください。申し出はそれ以外に何も入れていない独立したメッセージです:

> 「これはお見せしたほうが分かりやすいかもしれません。モックアップを入れたブラウザタブを開きましょうか？」

断られたらテキストのままで進め、相手自身が持ち出さない限り申し出を繰り返しません。

**質問ごとに問います: 見ることで分かりにくさが減りますか？** モックアップ、レイアウト、図、並べたデザイン案はブラウザへ。要件、スコープ、トレードオフ、概念上の選択はテキストに。UI の話題の質問が、自動的に視覚的な質問になるわけではありません。

相手が受け入れた場合は、サーバーを起動する前にこのディレクトリの `visual-companion.md` を読みます。
