# Superpowers の診断 (Diagnosing Superpowers)

## 概要

人間パートナーとともに何が悪かったかを特定し、ディスク上の transcript を読み、起きたことを証拠付きで報告します。あなたは報告します。superpowers を診断しません。バンドルや issue をトリアージする者が superpowers を変えるか決めます。

**コア原則:** すべての finding は `path:line` を引用します。引用なしに finding なし。すべての数値は transcript または実行したコマンド由来であり、記憶由来ではありません。

## ワークフロー

ステップごとに todo を作成します。ステップ 5–7 は記載条件でのみ実行します。

1. **問題の受け付け。** セッション群、判明していればターン範囲、パートナーが期待したこと、起きたこと、問題になる観測対象（ウォールクロック、トークン、繰り返し動作、特定の1動作）を書けるまで、一度に1つずつ質問します。「時間がかかりすぎる」は苦情であり問題記述ではありません。目標が superpowers バグレポートかも記録します。
2. **特定。** `references/session-discovery.md` を使って各セッションを検証済み絶対ファイルシステムパスに解決します。過去セッションは最初のプロンプトとタイムスタンプの引用で確認し、棄却した候補は理由付きですべて列挙します（なければ "none"）。サブエージェント transcript を列挙します。`~/.superpowers/diagnosing-superpowers/<session-id>/` を作成し、パートナーにパスを伝え、その来歴ルールに従って `templates/case.md` を記入します（環境とスキルの観測用）。
3. **トリアージ。** 報告された問題の周辺領域を自分で読みます。次に観点ごとにアナリストサブエージェントを1件ずつ並列派遣します。各件にケースファイルパス、`prompts/analyst-common.md`、および `prompts/` 内の観点ファイル1件（`skill-timeline.md`、`plan-adherence.md`、`repeated-work.md`、`stumbles.md`、`quality-evidence.md`、`request-conflicts.md`、`cost-and-time.md`）を渡します。transcript が長い場合は観点をターン範囲で分割します。`path:line` のない finding は破棄します。
4. **報告。** `templates/report.md` の全セクションを順に記入し、ワークスペースに書き、提示してパスを伝えます。引用内容が実際に何を証明するか確認し、裏付けケースを保持します。シンボリックリンクの別名は冗長複製ではありません。
5. **GitHub issues** — レポート §7 が possible または likely の場合、またはパートナーが求めた場合。`references/github-issues.md` に従って症状のオープン・クローズ済み issue を検索します。一致を示し、最も近いものへのレポート追加を提案します。一致がなければ `templates/issue.md` を記入し、ワークスペースに書き、正確な文面を示し、承認後にのみ issue を作成します。`gh` はファイルを添付できません。バンドルがあれば、ブラウザで添付できるようパートナーにパスを渡します。
6. **出力** — パートナーがバンドルを求めた場合のみ。求められずに構築してはなりません。受け付け目標がバグレポートだった場合、スクラブ済みバンドルが要求に応じて利用可能と1度だけ伝え、待ちます。秘匿化レベルを尋ね、各レベルの内容を述べます。skeleton（ツール結果本文なし）、evidence（引用イベントの本文のみ）、full（すべて）。`templates/bundle-README.md` に従ってバンドルを構築し、`prompts/scrub.md`、次に `prompts/scrub-audit.md` を派遣し、監査が CLEAN を返すまで両方を繰り返します。最終スクラブログ、ファイル一覧、プライバシーと証拠の結果を示す前に、バンドルテンプレートの証拠チェックと突き合わせを完了します。アーカイブ（`zip -r` または `tar -czf`）は承認後のみです。アーカイブパスとともに内容を述べ、置換はスクラブログを指し、スクラブは見逃すことがあると伝えます。共有前に全ファイルをレビューしなければなりません。
7. **類似セッション** — 求められた場合。確定 finding をシグネチャに変え、mtime とサイズで候補を列挙し、マーカー行番号を探し、候補ごとに `prompts/similar-session.md` を並列派遣し、レポート §9 に追記します。

## クイックリファレンス

7人のアナリストは常に全員実行します。この表は、ステップ3で自分が読む領域と、判定で先頭に置く finding を示します。

| 苦情 | 先に読むもの、先頭に置くもの |
|---|---|
| 「時間がかかりすぎる」 | cost-and-time、stumbles |
| 「なぜこの余計な作業をしたのか？」 | repeated-work、plan-adherence |
| 「なぜこんなに高価なのか？」 | cost-and-time |
| 「一体何をしているのか？」（実行中） | skill-timeline。網羅メモに進行中と記載 |
| 「計画を無視した」 | plan-adherence。圧縮行を先に |
| 「スキルXが起動しなかった」 | skill-timeline |

## 鉄則

- **コンテキスト安全。** 1 transcript 行が1メガバイトになることがあります。すべてのセッションファイルに毎回 `references/context-safety.md` に従います。
- **読み取り専用。** セッションファイルを変更・移動・削除してはなりません。
- **サブエージェントには正確なパスを。** サブエージェントの「現在のセッション」はそれ自身です。絶対パスと id を渡します。
- **人間プロンプトのみ。** フック出力、システムリマインダー、ツール結果はパートナーの言葉ではありません。サブエージェント transcript 内の "user" は親エージェントです。
- **superpowers の診断なし。** レポート §7 は関与を述べて止めます。スキルの欠陥を指名したり変更を提案したりしてはなりません。パートナーが修正を強く求めても免除されません。issue ステップを指し、要求に応じてバンドルが利用可能と伝えます。パートナーへの助言もしません。
- **承認ゲート。** パートナーがスクラブログとファイル一覧を見る前にアーカイブしません。正確な文面の承認前に issue やコメントを作成しません。
- **分析の前に受け付け。** パートナーが回答するまでステップ 2–7 を開始しません。不在なら質問を書いて停止します。再構成した記述は回答ではありません。既に範囲が定まった要求（特定の1イベント、現在実行中のもの、実行すべき分析）はそれ自体が記述です。回答してから尋ねます。セッション全体の「なぜ」は苦情です。

## レッドフラッグ

| 思考 | 現実 |
|--------|---------|
| 「問題は明らか、受け付けをスキップ」 | 問題記述がすべてを範囲付けます。尋ねます。 |
| 「不在だから記述を再構成する」 | パートナーが望んだことは再構成できません。質問を書いて停止します。 |
| 「今すべて掃引して最後に尋ねる」 | 範囲なしの掃引は誤った問いに予算を使います。先に尋ねます。 |
| 「バグレポートが欲しい、だから今バンドルを構築」 | バンドルはパートナーのセッションデータのパッケージです。求められた場合のみ構築します。 |
| 「小さな対象の編集、再構成は不要」 | あなたの判断ではありません。どれほど小さくても。証拠を報告し、トリアージする者が決めます。 |
| 「トークン単価はよく知られている」 | transcript から計算していない数値は創作です。引用か削除かです。 |
