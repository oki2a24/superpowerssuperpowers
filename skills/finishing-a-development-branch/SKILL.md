# 開発ブランチの完了 (Finishing a Development Branch)

## 概要

実装作業の完了をガイドし、明確なオプションを提示して、選択されたワークフローを処理します。

**コア原則:** テストの検証 → 環境の検出 → オプションの提示 → 選択の実行 → クリーンアップ。

**開始時の宣言:** 「実装を完了するために `finishing-a-development-branch` スキルを使用します。」

## アンチパターン

- **「後で直す」**: テストが失敗したままマージし、後で直すと約束すること。これは決して行われません。
- **検証のスキップ**: 最後に全テストを実行せずに完了を宣言すること。

## プロセス

### ステップ 1: テストの検証

プロジェクトのテストスイートを全て実行します（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**テストが失敗した場合:** 失敗を報告して停止します — メニューは緑のスイートの後にのみ表示されます：

```
テストが失敗しました（<N>件）。続行する前に修正が必要です：

[失敗の詳細を表示]
```

**テストがパスした場合:** ステップ 2 に進みます。

### ステップ 2: 環境の検出

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# ここで取得しておく（ワークスペース内にいる間に）— ステップ 5 でディレクトリを変更するため
# クリーンアップ（ステップ 6）はこの値を必要とする
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

これにより、表示するメニューとクリーンアップの方法が決定されます：

| 状態 | メニュー | クリーンアップ |
|-------|------|---------|
| `GIT_DIR == GIT_COMMON` (通常のレポジトリ) | 標準の3つのオプション | クリーンアップすべきワークツリーなし |
| `GIT_DIR != GIT_COMMON`, 名前付きブランチ | 標準の3つのオプション | 出所に基づく（ステップ 6 参照） |
| `GIT_DIR != GIT_COMMON`, デタッチド HEAD | 制限された2つのオプション（マージなし） | 外部管理 — そのまま残す |

### ステップ 3: ベースブランチの決定

ベースブランチは、この作業がフォークした元のブランチです — 通常、計画、会話、またはブランチの上流に記載されています。まだ不明な場合は尋ねます：「このブランチは `<最善の推測>` から分岐しました。正しいですか？」マージ前に確認してください：誤ったベースにマージすると、取り消すのが困難になります。

### ステップ 4: オプションの提示

**通常のレポジトリ、または名前付きブランチのワークツリーの場合 — 以下の 3 つのオプションを正確に提示します：**

```text
実装が完了しました。何をしますか？

1. ローカルで <base-branch> にマージする
2. プッシュしてプルリクエストを作成する
3. ブランチを現状維持する（後で自分で処理します）

どのオプションを選びますか？
```

**デタッチド HEAD の場合 — 以下の 2 つのオプションを提示します：**

```text
実装が完了しました。現在デタッチド HEAD（外部管理のワークスペース）にいます。

1. 新しいブランチとしてプッシュし、プルリクエストを作成する
2. 現状維持する（後で自分で処理します）

どのオプションを選びますか？
```

メニューは書かれている通りに正確かつ簡潔に提示してください。余計な説明は付け加えないでください。破棄（Discard）は、人間のパートナーが明示的に作業を捨てるよう求めた場合のみ実行されます（後述の「人間のパートナーから作業の破棄を求められた場合」を参照）。返答を待ってください。統合の決定はパートナーのものです。

### ステップ 5: 選択の実行

#### オプション 1: ローカルでマージ

```bash
# メインレポジトリのルートを取得（CWDの安全確保）
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 最初にマージを実行 — 何かを削除する前に成功を確認
git checkout <base-branch>
git pull
git merge <feature-branch>

# マージ後の結果でテストを検証
<test command>
```

マージ結果でテストが失敗した場合は、そこで停止し、ワークツリーとブランチをそのまま残して調査してください。何もプッシュされていないため、このマージはローカルのものであり復旧可能です。

マージ結果が成功した（テストがパスした）後にのみ、ワークツリーをクリーンアップ（ステップ 6）し、最後にブランチを削除します：

```bash
git branch -d <feature-branch>
```

#### オプション 2: プッシュしてプルリクエストを作成

```bash
git push -u origin <feature-branch>
# デタッチド HEAD の場合は、リモート側の新規ブランチ名を指定してプッシュします：
# git push origin HEAD:refs/heads/<new-branch>
```

その後、ホスティング環境（GitHub等）のツール（CLIがある場合は `gh` コマンドなど、無い場合はプッシュ時に出力される作成URL）を使用して、`<base-branch>` に対するプルリクエストを作成します。プロジェクトにPRテンプレートがある場合はそれに従い、作成したURLを人間のパートナーに報告します。

ワークツリーはクリーンアップしないでください。人間のパートナーがPRのフィードバックに対応するために、ワークツリーを必要とします。

#### オプション 3: 現状維持

「ブランチ `<name>` を保持します。ワークツリーは `<path>` に維持されます。」と報告します。

#### 人間のパートナーから作業の破棄を求められた場合

このパスは、作業を破棄するように明示的に要求された場合のみ実行されます。実行前に、まず確認を求めてください：

```text
これは永続的に削除されます：
- ブランチ <name>
- すべてのコミット: <commit-list>
- <path> のワークツリー

確認のために 'discard' と入力してください。
```

正確な確認の入力を待ってください。入力が得られた場合：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

その後、ワークツリーをクリーンアップ（ステップ 6）し、ブランチを強制削除します：

```bash
git branch -D <feature-branch>
```

## ステップ 6: ワークツリーのクリーンアップ

**オプション 1 の実行時、および確認済みの破棄の場合にのみ実行します。** オプション 2 と 3 では常にワークツリーを保持します。呼び出し元はすでにメインリポジトリのルートに移動しています（ワークツリーの削除はワークツリーの外から実行する必要があります）。ステップ 2 で事前に取得した `GIT_DIR`、`GIT_COMMON`、`WORKTREE_PATH` を使用します。

**`GIT_DIR == GIT_COMMON` の場合:** 通常のリポジトリであり、クリーンアップすべきワークツリーはありません。完了です。

**`WORKTREE_PATH` が `.worktrees/` または `worktrees/` の配下にある場合:** 私たちが作成したワークツリーであるため、クリーンアップを行います：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 自律修復: 古い登録情報を整理
```

**削除が拒否された場合** (`contains modified or untracked files`): ワークツリーには他に存在しないファイルが含まれています — 未コミットの計画、メモ、作業中のファイルなど。自分の判断で `--force` してはいけません。まず人間パートナーに状況を示し、以下で尋ねてください:

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
Worktree removal refused — these files were never committed:

<file list>

1. Commit them to <branch> before cleanup
2. Move them into <main repo root>
3. Delete them (unrecoverable)

Which?
```

選択に応じて実行し、その後ワークツリーを削除します。

**それ以外の場合:** ホスト環境（ハーネス）が作成したワークスペースであるため、削除しないでください。プラットフォームがワークスペース終了ツールを提供している場合はそれを使用し、そうでない場合はそのまま残します。

## クイックリファレンス

| オプション | マージ | プッシュ | ワークツリー保持 | ブランチ削除 |
| :--- | :---: | :---: | :---: | :---: |
| 1. ローカルマージ | ✓ | - | - | ✓ |
| 2. PR 作成 | - | ✓ | ✓ | - |
| 3. 現状維持 | - | - | ✓ | - |
| 破棄 (明示的な要求のみ) | - | - | - | ✓ (強制) |

## 自己正当化の防止 (Common Rationalizations)

| 言い訳 | 現実 |
|--------|---------|
| 「テストはセッションの早い段階でパスした」 | 統合しようとしているツリーでテストスイートを実行してください。成功した実行は、それが実行されたツリーのみを証明します。 |
| 「マージを望んでいるのは明らかだ」 | 統合は人間のパートナーの決定です。メニューを提示して待ってください。 |
| 「この機能の作業は終わったようだ。破棄を提案しよう」 | メニューは書かれている通りに完成しています。破棄は、人間のパートナーが言葉で明示的に求めた場合にのみ発生します。 |
| 「『ああ、それ消しといて』のような言葉も確認として扱ってよい」 | typed word である `discard` という単語のみが削除を許可します。 |
| 「PRを作成したから、もうワークツリーは不要なゴミだ」 | PRのフィードバックはそのワークツリーで修正されます。作業がマージされるまで保持してください。 |
| 「この別のワークツリーは古そうだから、ついでにクリーンアップしよう」 | `.worktrees/` または `worktrees/` の下のワークツリーのみをクリーンアップしてください。それ以外はすべてホスト環境に属します。 |
| 「削除が拒否された — `--force` は単にクリーンアップを完了させるだけだ」 | 拒否はそのワークツリーにしか存在しないファイルを意味する。`--force` はそれらを永続的に破壊する。人間パートナーに状況を示し、尋ねてください。 |
| 「マージ結果のテスト失敗は、おそらく不安定な（flaky）テストのせいだ」 | マージ結果の失敗はすべてを停止させます。調査中はブランチとワークツリーをそのまま残してください。 |
| 「ベースブランチは明らかに main だ」 | 分岐点を確認するか、尋ねてください。誤ったベースにマージすると、取り消すのが困難になります。 |
| 「プッシュが拒否された。強制プッシュ（force-push）で解決しよう」 | プッシュの拒否はリモートが移動したことを意味します。調査してください。強制プッシュは人間のパートナーの明示的な要求がある場合にのみ実行します。 |
