# サブエージェント駆動開発 (Subagent-Driven Development)

実装計画のタスクごとに新しい実装者サブエージェントを派遣し、各タスクの後に仕様準拠性と品質をレビューし、最後にブランチ全体をレビューして実行します。

**中核原則:** タスクごとの新しい実装者 + タスクレビュー + 最終レビューにより、コンテキストを分離し、各段階で検証します。ナレーションはツール呼び出し間に短く1行までとし、台帳とツール結果に進捗を残します。

## 継続実行と裁定

タスク間で人間との確認のために一時停止せず、計画の全タスクを実行します。計画の衝突、曖昧さ、欠陥、上限超過は、仕様 (Spec) を権威として判断します。Spec も計画も答えを定めていない点はコントローラー自身の判断で裁定し、いずれも台帳に次の形式で記録して続行します。

`Ruling: <決定> — <理由> — <誤っていた場合のコスト>`

停止して人間に確認するのは次の4つだけです。
1. 不可逆または破壊的な操作。
2. セキュリティ上慎重な扱いが必要な操作。
3. 規範上事前確認が必要なワークツリー外への副作用（マージ、共有ブランチへの push、公開など）。
4. 計画が破綻し、前進するすべての経路が推測になる場合。

## いつ使用するか

次のすべてに該当する場合、この方式を使います。
- 実装計画がある。
- タスクの大部分が独立している。
- 人間がインライン実行を選んでおらず、サブエージェント機能が利用できる。

計画がない場合、タスクが密結合の場合は、この方式ではなく手動実行または先行するブレインストーミングを選びます。人間がインライン実行を選ぶ場合、またはサブエージェント機能がない場合は `executing-plans` を使用します。

`executing-plans` と同様、同じセッションで計画ワークスペースと台帳を共有し、タスク間で停止しません。この方式はタスクごとに新しい実装者とレビュー担当者のコンテキストを使い、インライン方式は実装者1つのコンテキストと最後のレビュー担当者だけを使います。

## プロセス

1. セットアップ、台帳の復旧、計画と Spec の確認、事前スキャンを行います。
2. 未完了タスクごとに、実装者を1人だけ派遣します。実装者は実装、テスト、コミット、セルフレビューを行います。
3. タスク概要、実装レポート、差分パッケージを渡して、新しいタスクレビュアーを派遣します。Spec 準拠と品質の両方が承認されるまでタスクを完了にしません。
4. 指摘がある場合は最大5回の修正・スコープ付き再レビューを行います。計画との衝突は裁定して台帳に残します。
5. 全タスク後にブランチ全体をレビューし、必要なら修正派遣1回と再レビュー1回を行います。
6. 最終レビューが完了したら、この計画のワークスペースだけを削除し、`finishing-a-development-branch` を使います。

## セットアップ

作業は隔離されたワークスペースで行います。`using-git-worktrees` を使って作成するか、現在の環境が既に隔離されていることを確認します。人間の明示的な同意なしに `main` / `master` 上で実装を開始しません。

会話の記憶はコンテキスト圧縮を生き残りません。todo だけでなく、台帳ファイルで進捗を追跡します。

1. **計画のワークスペースを特定:** このスキルのディレクトリで `bash scripts/sdd-workspace PLAN_FILE` を実行します。計画専用の git-ignored ディレクトリ（リポジトリの `.superpowers/sdd/` 配下）が、台帳、概要、レポート、レビュー用パッケージの置き場です。他の計画のディレクトリを読んだり書いたりしません。
2. **既存台帳を確認:** `<workspace>/progress.md` の先頭行が対象計画を示す場合、`Task <N>: complete` と記録されたタスクを再派遣せず、最初の未完了タスクから再開します。末尾が修正ラウンドなら次ラウンドから続けます。別計画を指す台帳や旧形式の `.superpowers/sdd/progress.md` は他の計画のものとして残し、新しい台帳を開始します。
3. **台帳を作成:** 先頭行を `# SDD ledger — plan: <plan file path>` とします。コミットは Git に記録されるので、圧縮後は台帳と `git log` を自分の記憶より優先します。`git clean -fdx` は git-ignored の作業領域を消すため実行しません。消失した場合は `git log` から復旧します。
4. **計画と Spec を読む:** 計画を一度読み、コンテキストと Global Constraints を記録し、全タスクの todo を作ります。Spec が指定されていれば読み、権威として扱います。Spec に到達できない場合は台帳に記録し、その状態での裁定は暫定とします。
5. **タスク着手前の衝突スキャン:** タスク間で共有するファイルまたはインターフェースの組ごとに、片方の成果物と他方の入力、衝突の有無を表にします。各タスクについて、タスク内の矛盾（要求するテストとコード、作成するファイルと後で変更するファイルなど）も1行ずつ記録します。「問題なし」だけで表を省略してはいけません。Spec と計画の衝突、計画がレビュー基準上の欠陥を明示的に要求する場合も、実行開始前に Spec を権威として裁定し、各行の横に Ruling を記録します。

## モデル選択

速度とコストのため、役割を扱える範囲で最も能力の低いモデルを使います。

- **機械的な実装**（明確な仕様の1〜2ファイル変更）は高速・低コストモデル。
- **統合や判断**（複数ファイルの調整、パターン照合、デバッグ）は標準モデル。
- **設計・アーキテクチャと最終ブランチレビュー**は利用可能な最上位モデル。最終レビューをセッションの既定モデルに任せてはいけません。
- **通常レビュー**は差分の規模、複雑さ、リスクに合わせます。小さく機械的な差分は低〜中位でよく、複雑・高リスクな差分には上位を使います。
- **修正ラウンド4〜5**は、行き詰まった実装者より少なくとも1段上のモデルを使います。

派遣時はモデルを必ず明示します。省略するとセッションのモデルが暗黙に継承されます。最安モデルは複数ターン必要となり総費用が増えることがあります。文章仕様から実装する担当者やレビュアーには中位モデルを下限とし、タスク複雑度とターン数も総コストとして考慮します。

## タスクサイクル

### 1. 実装者を派遣する

実装者を派遣する前に `git rev-parse HEAD` で BASE SHA を記録します。レビューと修正差分に使い、複数コミットの途中を落とす `HEAD~1` で代用してはいけません。

- `bash scripts/task-brief PLAN_FILE TASK_NUM` を実行し、計画の完全なタスク本文が入った概要ファイルを作ります。概要を唯一の要件出典とし、実装者に計画全体を読ませません。
- 派遣には、この作業がプロジェクトのどこに当たるかの1行、最初に読む概要ファイルのパス、概要にない依存・インターフェース・前タスクの裁定、必要な場合だけ曖昧さの解決、レポートファイルのパスと契約を含めます。正確な値、数値、シグネチャ、テストケースは概要だけに置きます。
- タスク概要 `task-N-brief.md` に対応するレポートは `task-N-report.md` とし、実装者が詳細を書きます。実装者には状態、コミット、テストの一行要約、懸念だけを返させます。
- 後のタスクには、必要なインターフェースと全体制約だけを渡し、過去タスクの長い要約や会話履歴を貼りません。先行台帳にその領域の保留指摘があれば、台帳の位置を知らせます。
- 実装者は自分のタスクを完了し、別のサブエージェントを起動しません。レビューはコントローラーが報告後に派遣します。実装サブエージェントを複数同時に派遣しません。派遣結果のエージェント識別子は記録し、1〜3回目の修正で再開します。
- 形が同じ小さな編集を計画が複数タスクに分けている場合、1回の概要に全ファイルと変更を列挙してまとめて派遣します。独自の判断・テスト・レビュー範囲が必要なタスクは分けたままにします。

**派遣した子を待つ場合:** 短いタイムアウトで待機 API をポーリングせず、無言のまま無期限に待ち続けません。台帳更新や次のレビュー準備など手元の作業がある間は続行し、待機が必要な状態になってから5〜10分の範囲で待ちます。各待機の後に短い状況行を出して子の一覧を確認し、完了しているのに報告がない子には連絡します。短時間のポーリングを重ねてはいけません。

### 2. 実装者の報告を処理する

- **`DONE`:** `bash scripts/review-package PLAN_FILE BASE_SHA HEAD_SHA` を実行し、表示された差分パッケージをタスクレビュアーへ渡します。
- **`DONE_WITH_CONCERNS`:** 懸念を読んでから進みます。正確性や範囲の問題ならレビュー前に解決し、単なる観察なら記録してレビューへ進みます。
- **`NEEDS_CONTEXT`:** 不足情報を補って再派遣します。
- **`BLOCKED`:** 原因を見極め、文脈不足なら補足して同じモデルで再派遣、推論不足なら上位モデル、規模過大なら分割、計画の誤りなら裁定を台帳に記録してから再派遣します。エスカレーションを無視したり、変更なしで同じモデルに繰り返させたりしません。

質問があれば、作業前でも途中でも、完全に回答し必要な文脈を補います。

### 3. タスクをレビューする

各タスクのレビューは必須のゲートです。仕様準拠性とタスク品質の両方の判定がなければ承認しません。実装者のセルフレビューはタスクレビューの代わりになりません。

- `bash scripts/review-package PLAN_FILE BASE_SHA HEAD_SHA` でレビュー用ファイルを作り、そのパスを渡します。このスクリプトは範囲を検証し、`BASE..HEAD` が空または子孫関係でなければ exit 3 にします。別ブランチの変更を「差分なし」と誤認してはいけません。スクリプトを使えない場合は、コミット一覧、`git diff --stat`、`git diff -U10` を一意なファイルにまとめます。レビュアーに差分ファイルを渡さず派遣してはいけません。
- レビュアーには同じタスク概要、実装者レポート、レビュー用パッケージ、およびそのタスクを拘束する Global Constraints を渡します。制約は計画または Spec から正確に転記し、正確な値・形式・関係性を保ちます。レビュアーに結論を先取りさせたり、「指摘しないで」と指示したりしてはいけません。
- レビュアーは範囲を越えてコードベースを探索しません。差分外は具体的なリスクを名指しした焦点の絞られた確認だけ許可します。レビュアーは読み取り専用です。分割レビューや第二意見のためのサブエージェントも派遣しません。
- レポートのテストを同じコードで再実行させません。証拠が読めない・切れている場合、コントローラーが記載パスを読み直します。実際に証拠が欠落していた場合はギャップとして扱い、再テストで読めなかった記録を作り直しません。
- 一括変更はファイルごとに要件と差分を照合します。肯定判定を含む確認項目と全指摘には `file:line` の根拠を付けます。構造、テスト範囲、テスト出力がクリーンか、実装者の強み、深刻度も確認します。
- レビュアーが「差分から検証不能」とした項目は、コントローラーがタスク完了前に解決します。実際のギャップなら失敗判定として修正ループに含めます。

### 4. 修正ループ

Spec の FAIL、Critical/Important の指摘、または実際のギャップと確認した ⚠️ があれば修正ループに入ります。Minor は `Task <N>: minor (deferred): <要約>` と台帳に記録し、最終レビューのトリアージに渡します。計画が明示的に要求する内容、または指摘と計画文が衝突する内容は、Spec を権威としてコントローラーが裁定し、その指摘を無視せず、修正前に Ruling を台帳へ記録します。

1タスクにつき、修正派遣とスコープ付き再レビューを合わせて最大5ラウンドです。

- **1〜3回目:** 元の実装者に指摘をそのまま渡して再開します。ハーネスで継続メッセージを送れない場合のみ、新しい実装者を概要、レポート、指摘とともに派遣します。
- **4〜5回目:** 概要、レポート、指摘を渡し、より能力の高い新しい実装者に引き継ぎます。何を試したかをレポートで確認するよう伝えます。
- **各ラウンド:** 実装者は修正し、変更をカバーするテストを再実行し、同じレポートへ変更・テスト名・実行コマンド・出力を追記します。再レビューを派遣する前に、その証拠が揃っていることをコントローラーが確認します。
- `FIX_BASE_SHA` は直前のレビューが見た HEAD とし、`bash scripts/review-package PLAN_FILE FIX_BASE_SHA HEAD_SHA` のパッケージで `re-review-prompt.md` によるスコープ付き再レビューを依頼します。指摘ごとに ADDRESSED / NOT ADDRESSED を判定し、修正差分が新たに生んだ Critical/Important も未解決一覧に加えます。差分外の観察は台帳に保留し、ループを広げません。
- 各ラウンド後、台帳に `Task <N>: fix round <R>/5 (<対応数> addressed, <未解決数> open — <要約>; commits <開始>..<終了>)` を追記します。コントローラー自身が修正してレビューを迂回してはいけません。
- 5回目の再レビューにも指摘が残れば、それぞれを裁定します。誤り・議論可能、または後続に影響しない実問題は理由を添えて保留し、最終レビューへ渡します。後続を妨げる実問題は、前進可能にする最小限の判断を台帳に記録し、後続へ引き継ぎます。停止するのは、全経路が推測となる場合だけです。上限到達を理由に一律 BLOCKED にしてはいけません。

### 5. タスクを完了する

レビューがクリーン、または5回の上限時にすべての未解決指摘を裁定・記録したら、台帳に完了行を記録し、todo を完了にします。

- `Task <N>: complete (commits <base7>..<head7>, review clean)`
- 上限後に保留事項があれば `Task <N>: complete (commits <base7>..<head7>, <K> parked)`

Critical/Important の指摘を修正せず、上限時の裁定もせずに次のタスクへ進みません。

## ブランチ全体の最終レビュー

全タスクの完了後、`bash scripts/review-package PLAN_FILE MERGE_BASE HEAD_SHA` でブランチ開始点から HEAD までのパッケージを作ります。最上位の能力を持つモデルで `requesting-code-review/code-reviewer.md` によるレビューを派遣し、台帳の保留 Minor と裁定済み指摘も渡してトリアージさせます。

最終レビューに指摘があれば、全件をまとめて1人の修正担当へ1回だけ派遣し、修正範囲のスコープ付き再レビューを1回だけ行います。残った指摘はタスクループと同様に裁定します。2回目の修正派遣は行いません。最終レビュー後に残る load-bearing な指摘は `finishing-a-development-branch` で選択肢を示す際に人間へ伝えます。

## 完了処理

作業領域を削除する前に、事前裁定、保留指摘、上限時の判断を含め、台帳内のすべての `Ruling:` 行を発生順に最終報告の「行った裁定」欄へ列挙し、それぞれ誤っていた場合のコストも記載します。これは人間が判断と必要な手戻りを確認できる唯一の一覧です。

最終レビューと必要な修正が完了した後、この計画自身のワークスペースだけを削除します。兄弟の計画ディレクトリには触れません。その後、`finishing-a-development-branch` を使用します。

## よくある自己正当化

| 言い訳 | 現実 |
|---|---|
| 「仕様にはほぼ合っている」 | Spec の指摘があるなら未完了です。修正するか、上限後に裁定します。 |
| 「自分で直す方が早い」 | コントローラーの修正はレビューを迂回し、調整役の文脈も汚します。実装者を再開します。 |
| 「あと1回やれば収束する」 | 上限後は修正ループを回さず裁定します。 |
| 「レビュアーはまた新しい指摘を出す」 | 再レビューは修正範囲に限定します。未変更箇所の観察は台帳へ送ります。 |
| 「指摘は明らかに間違いだから捨てる」 | 上限までは裁定せず、上限後も理由を台帳に残します。黙って破棄しません。 |
| 「修正が小さいので再レビューを省く」 | 各修正ラウンドの終わりには必ずスコープ付き再レビューをします。 |
| 「レビューは遅い」 | レビューなしのループは検証されない変更の繰り返しです。 |
| 「台帳は余分な作業だ」 | 台帳はコンテキスト圧縮後に完了済みタスクの再実行を防ぎます。 |
| 「実装者が独自レビュアーも起動した」 | レビュー席の重複です。実装者の契約違反として扱います。 |

## 実行例

```text
[計画用ワークスペースを確認し、計画を読んで todo を作成]
[task-brief で Task 1 の概要を作り、BASE SHA とレポート先を指定して実装者を派遣]
実装者: DONE — コミットとテスト要約を報告し、詳細レポートを保存
[review-package を作成し、概要・レポート・diff と Global Constraints をレビュアーへ渡す]
レビュアー: Spec に不足を検出
[実装者を再開して修正。カバーするテストのコマンドと出力をレポートへ追記]
[修正 diff を使ってスコープ付き再レビュー。指摘が対応済みと確認]
[Task 1 の完了を台帳に記録し、Task 2 へ進む]
[全タスク後、merge-base から HEAD までを最上位モデルでレビュー]
[全 Ruling と保留を報告し、最終確認後にこの計画のワークスペースを削除]
```
