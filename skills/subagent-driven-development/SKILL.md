# サブエージェント駆動開発 (Subagent-Driven Development)

タスクごとに新しい実装者サブエージェントをディスパッチし、各タスク後にタスクレビュー（仕様準拠性 + コード品質）を行い、最後にブランチ全体の広範なレビューを行って計画を実行します。

**なぜサブエージェントなのか:** 隔離されたコンテキストを持つ専門化されたエージェントにタスクを委任します。彼らの指示とコンテキストを精密に作成することで、彼らが集中してタスクに成功することを保証します。彼らがあなたのセッションのコンテキストや履歴を継承することは決してありません — あなたは彼らが必要とするものを正確に構築します。これにより、調整作業のためのあなた自身のコンテキストも保護されます。

**コア原則:** タスクごとのフレッシュなサブエージェント + タスクレビュー（仕様 + 品質） + 最終的な広範レビュー = 高品質、高速なイテレーション

**ナレーション (Narration):** ツール呼び出しの間、ナレーションは高々1行の短い文で行います — 台帳（ledger）とツールの実行結果が記録を保持します。

**継続実行 (Continuous execution):** タスク間でユーザーとの確認のために一時停止しないでください。停止することなく計画からすべてのタスクを実行します。停止する唯一の理由は: 解決できない BLOCKED ステータス、進行を真に妨げる曖昧さ、またはすべてのタスクの完了です。「続行すべきですか？」という促しや進捗要約は時間を無駄にします — ユーザーは計画の実行を求めたので、それを実行してください。

## いつ使用するか

**計画の実行 (Executing Plans - 並行セッション) との比較:**
- 同じセッション（コンテキスト切り替えなし）
- タスクごとにフレッシュなサブエージェント（コンテキスト汚染なし）
- 各タスク後のレビュー（仕様準拠性 + コード品質）、最後に広範なレビュー
- 高速なイテレーション（タスク間で人間のパートナーの介在なし）

## プロセス (The Process)

### セットアップ (Setup)

`using-git-worktrees` スキルを使用して、隔離されたワークスペースで作業が行われていることを確認します。人間のパートナーの明示的な同意なしに、`main`/`master` ブランチで直接実装を開始しないでください。

会話のメモリはコンテキスト圧縮を生き残れません。実際のセッションにおいて、位置を見失ったコントローラーが完了したタスクシーケンス全体を再ディスパッチしてしまう現象が観察されています — これは観察された中で最もコストのかかる失敗です。todo だけでなく、**台帳ファイル (ledger file)** で進捗を追跡してください。

1. **台帳ファイルの初期化:**
   `.git/sdd-ledger-[plan-name].md` またはワークスペース内の `.sdd-ledger-[plan-name].md` に台帳を作成します。
   ```markdown
   # SDD Ledger: [Plan Name]
   Plan: [path/to/plan.md]
   Workspace: [path/to/workspace]
   Started: [TIMESTAMP]

   ## Tasks
   ```

2. **事前レビュー (Pre-flight Review):**
   計画全体を批判的にロードして確認します。矛盾、依存関係の循環、明確化が必要な領域を特定します。ブロッカーが存在する場合は、作業を開始する前にユーザーにエスカレーションしてください。

### タスクごとのサイクル (Per-Task Cycle)

計画内の各未完了タスクについて:

1. **タスク概要の準備:**
   `scripts/task-brief PLAN_FILE TASK_NUM` を使用してタスク概要ファイルを生成します。

2. **実装者サブエージェントのディスパッチ:**
   `implementer-prompt.md` テンプレートを使用して `general-purpose` サブエージェントを起動します。
   - モデル選択規律に従って適切なモデル（pro/flash等）を指定します。
   - 実装者に作業を行わせ、セルフレビューと TDD 証拠を含むレポートを提出させます。

3. **タスクレビューの実行:**
   実装者が完了したら、`scripts/review-package PLAN_FILE BASE_SHA HEAD_SHA` を実行してレビューパッケージを作成します。
   - `task-reviewer-prompt.md` テンプレートを使用してレビュアーサブエージェントをディスパッチします。
   - 仕様準拠性とコード品質の2つの軸で判定を受けます。

4. **修正ループ (Fix Loops & 5-Round Breaker):**
   レビューで Critical または Important な指摘事項が出た場合、修正ラウンド（最大5ラウンド）に入ります。
   - **R ≤ 3 (再開ループ):** 前回の実装者サブエージェントのセッションにメッセージを送り（`send_message`）、指摘事項の修正を指示します。
   - **R ≥ 4 (ブレーク対策):** 同一エージェントでの修正が行き詰まっていると判断し、**新しい実装者サブエージェント**をより能力の高いモデル（例: `pro`）でディスパッチします。
   - 修正完了後、`re-review-prompt.md` を使用してスコープ付き再レビューを実施します。
   - **5ラウンド到達時 (Breaker Trips):** 5ラウンド目の再レビューでも指摘事項が残る場合、修正ループを自動停止（裁定モード）します。残った指摘事項を査定し、それが本質的（load-bearing）な問題であればユーザーに `BLOCKED` を報告して停止します。軽微または方針合意済みの場合は台帳に記録してタスクを通過させます。

5. **タスクの完了記録:**
   指摘事項がクリアされたら、台帳ファイルに完了を記録し、todo のチェックボックスを更新します。

### ブランチ全体の最終レビュー (Final Code Review)

すべてのタスクが完了したら:

1. **全体コードレビューのディスパッチ:**
   `requesting-code-review/code-reviewer.md` テンプレートを使用して、ブランチ全体の差分（計画開始時 SHA 〜 最新 SHA）に対するコードレビューをディスパッチします。
2. **1回限りの最終修正ディスパッチ (Single Fix Dispatch):**
   最終レビューで指摘事項が出た場合、最大1回の修正ディスパッチと1回のスコープ付き再レビューを認めます。残存する問題は台帳に裁定記録を残して終了します。
3. **ワークスペースの整理:**
   最終レビューがクリーンになったら、`finishing-a-development-branch` スキルを起動して作業の統合（マージ / PR / 現状維持）をユーザーにガイドします。

## モデル選択プロトコル (Model Selection)

サブエージェントをディスパッチする際は、タスクの複雑さに応じて適切なモデルを選択します：
- **標準的なタスク実装・通常レビュー:** プラットフォームの標準/高速モデル (e.g. `flash` / `inherit`)
- **複雑なリファクタリング、R ≥ 4 の修正、高度なアーキテクチャ設計:** 最上位モデル (e.g. `pro`)

モデル指定を省略すると最も高価なモデルが暗黙的に継承されるため、必ず明示的にモデルを指定してください。

## 自己正当化の防止 (Common Rationalizations)

| 言い訳 | 現実 |
|--------|---------|
| 「タスクが簡単だから、レビューなしで直接自分でコードを書こう」 | SDDの目的は隔離と検証です。タスクが小さくても実装者サブエージェントをディスパッチし、レビューを受けてください。 |
| 「サブエージェントに会話履歴全体を渡した方が文脈が伝わる」 | コンテキストの汚染を防ぐため、精密に構築したタスク概要ファイルのみを渡してください。 |
| 「修正ループが長引いているが、手動でコードを直して終わらせてしまおう」 | コントローラーが直接コードを編集すると規律が崩れます。5ラウンドブレーカーの裁定プロトコルに従ってください。 |
| 「最終レビューの指摘事項を直すために、何回も修正ループを回そう」 | 最終レビューでの修正ディスパッチは最大1回です。残存問題は裁定記録を残して人間のパートナーの判断に委ねてください。 |

## 2026-08-13 上流 v6.3.0 同期ノート

**継続実行規律の強化**
* 停止は4条件のみ: 不可逆/破壊的操作、セキュリティ敏感アクション、ワークツリー外への副作用要確認（マージ/プッシュ等）、計画が破綻して全パスが推測に等しい場合。
* その他は **Ruling** 文化: 決定を台帳に `Ruling: <決定> — <理由> — <誤った場合のコスト>` として記録し継続。
* 計画衝突スキャン: 実行前にタスク間のファイル/インターフェース共有をテーブル化し、Spec を権威としてルール化。
* 修正ループ: 衝突は人間に聞かずルール化、ブレーカー到達時は裁定して継続。
* バッチ小タスク: 同形小編集は1ディスパッチに束ねる。
* 待機ポリシー: 短時間ポーリング禁止、5-10分バウンデッド待機 + ステータス1行。
* Implementer 契約: サブエージェントは決してサブエージェントを起動しない。
* 最終メッセージに全 Ruling 一覧を集約して人間へ引き渡す。
