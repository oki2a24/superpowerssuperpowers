# 良いテストの書き方 (Writing Good Tests)

本ドキュメントは、テストを価値あるものにするためのルールを定義します。これはテストの新規作成時やリファクタリング時、またはテスト用クリーンアップ/ヘルパーメソッドの追加時に参照してください。

## 概要

テストは特定の問題（破壊・バグ）を捕まえるために存在します。ここでは2つの原則がすべてを規定します：

```
1. すべてのテストは、それが捕まえる「破壊」に明確な名前をつける
2. すべてのテストは本物（実コンポーネント）を動かす
```

厳格な TDD は、この両方を自然に生み出します。最初に書き、実コードに対して失敗することを確認したテストは、すでにそれが失敗できることを物理的に証明しています。そして、実依存関係が遅い、または外部システムであると証明された場合にのみモックが許容されます。

## 原則 1: 破壊に名前をつける (Name the Break)

テスト本体を書く前に、次の質問に答えてください：**「どのようなプロダクションコードの変更がこのテストを失敗させるか — そしてその変更はバグか、それとも単なる意思決定（設計変更）か？」** テストは、誤った分岐、不足している副作用、誤った引数、境界条件、または破られた契約を捕まえることで、その存在意義を得ます。

**期待値は独立して導出する。** リテラルや手動検証済みのフィクスチャを使用してください。リテラルな `want` 値を持つテーブル駆動テストが推奨される形態です。テスト対象のコード（またはそのヘルパー）によって計算された期待値は、そのコードが何をしようとパスしてしまいます：

```typescript
// ❌ ミラーアサーション: 同じビルダーが両辺を計算している — 常に true になってしまう
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手動で導出したリテラル
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**チェンジ・ディテクター（変更検知器）にしない。** 意図的な意思決定（定数の値、メッセージの正確な文言、プライベート構造）だけでテストが失敗する場合、それはリデザイン（再設計）のたびに誤検知して壊れ、本当のバグをスルーします。意思決定に依存する「挙動」をテストしてください。`expect(MAX_RETRIES).toBe(5)` ではなく、「失敗した呼び出しは5回リトライされ、6回目の試行は発生しない」ことを確認します。

**テキストではなく挙動をテストする。** スクリプト、スキル、または設定ファイルが正確な行を含んでいることをアサートすることは、ソースがソースであることを証明するだけに過ぎません。制御された入力に対してスクリプトを実行し、出力、副作用、または終了コードをアサートしてください。エージェントに指示を与えるドキュメントは、それを利用するエージェントの挙動によってテストされます（`superpowers:writing-skills`）。人間向けの文章にはテストは不要です。

**フレームワークではなく、あなたのコードをテストする。** あなたのコードがその境界で結ぶ契約 — 登録するルート、発行するクエリ、生成するペイロード — をテストしてください。上流（フレームワーク等）のメカニズムは、そのメンテナが書くべきテストです（典型例: ルーターが登録されたハンドラーを呼び出すことのアサート — それはフレームワークのテストであり、あなたのテストではありません）。上流の挙動に本気で驚かされた場合は、その前提に名前をつけた狭い確認テストを1つ書いてください。同じ境界はあなたのコード内部にも適用されます: コンストラクタ、ゲッター、定数、および軽微な転送機能は、それらが検証、正規化、デフォルト設定、導出、強制、または副作用を引き起こす場合にのみテストする価値があります。それ以外の場合は、それらに依存する最初のユーザー可視の結果をアサートしてください。

### ゲートファンクション (Gate Function)

```
テスト本体を書く前に:
  このテストを失敗させるプロダクションコードの変更名を挙げる。

  挙げられない                → 観察可能な挙動を中心に再設計する
  「ソーステキストが変更された」  → 成果物を実行し、その効果をアサートする
  意図的な意思決定のみ         → チェンジ・ディテクターである。その決定に
                               依存する「挙動」をテストする

  期待値がテスト対象コードなしで導出されていることを確認する。
  もしテスト対象コードのロジックやヘルパーを再利用している場合:
    リテラルまたは手動確認済みのフィクスチャに置き換える
```

## 原則 2: 本物を動かす (Exercise the Real Thing)

**モックはアサーションを獲得しない。** モックに対するアサーションは、モックが存在するときにパスし、存在しないときに失敗します — それはコンポーネントについて何も言っていません。実コンポーネントの挙動をアサートしてください。チェックしているのがモック自体であれば、モックを解除するか、アサーションを削除してください。

```typescript
// ✅ 実際の挙動
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ モックの存在確認
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**パートナーからの指摘:** 「私たちはモックの挙動をテストしているのですか？」

**適切なレベルでモックする。** 実際のメソッドを置き換える前に、そのすべての副作用を把握してください。遅い操作や外部操作のみをモックし、テストが依存する部分は本物のまま維持します。確信が持てない場合は、まず本物の実装に対してテストを実行し、実際に何が起こる必要があるかを観察してください。

```typescript
// ❌ 重複検知が読み込む設定書き込みをモックが握りつぶしてしまう
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ サーバーの遅い起動のみをモックし、設定書き込みは本物のまま維持する
vi.mock('MCPServerManager');
```

**テストダブル（擬似オブジェクト）を具体的にする。** 引数、呼び出し回数、または順序が契約の一部である場合は、それらをアサートしてください — 何でも受け入れるフェイクは何も検証しません。成功、エラー、不正形式の各ブランチに専用のフィクスチャまたはスパイを与え、誤ったブランチが期待を満たせないようにします。

**本物のデータを完全に模倣する。** テストが読み込むフィールドだけでなく、現実に存在する完全な構造（文書化されている全フィールド）をモックしてください。部分的なモックは、下流のコードが省略されたフィールドを読み込んだときに静かに失敗します: テストはパスするのに統合環境で壊れる原因になります。

**プロダクションクラスにはプロダクションメソッドのみを置く。** テストのためだけに用いられるクリーンアップはテストユーティリティ内に配置し、プロダクションクラスの `destroy()` などとして置かないでください。問うてください: このメソッドはテストからしか呼び出されないか？このクラスはこのリソースのライフサイクルを所有しているか？答えが「いいえ」なら → テストユーティリティに移動してください。

**複雑なモックより実コンポーネントを優先する。** モックのセットアップがテストロジックより大きくなった場合、モックに実コンポーネントが持つメソッドが欠けている場合、またはモックの変更でテストが壊れる場合は、実コンポーネントを使用した統合テストに切り替えてください。 **パートナーからの質問:** 「ここで本当にモックを使う必要がありますか？」

### ゲートファンクション (Gate Function)

```
モックやテストヘルパーを追加する前に:
  実メソッドの副作用を列挙する。テストが依存するものは
  本物のまま残し、その下の遅い/外部レベルをモックする。

  モックのレスポンスは完全な実構造を模倣する。

  テストからしか呼び出されないメソッドはプロダクションではなく
  テストユーティリティに置く。

  モック自体に対してアサートしようとしているか？
    モックを解除するか、アサーションを削除する。
```

## テストは実装と共に出荷する (Tests Ship With the Implementation)

TDD サイクル — 失敗するテスト、最小限の実装、リファクタリング — これが「完了」の定義です。挙動が必要とするテストのみを出荷してください: トラビアルな（自明な）コードや人間用の文章にはテストは不要であり、プロセスのために書かれたテストは永久に保守コストを引き起こします。

## ミューテーションチェック (The Mutation Check)

作業を終える前に、心の中でプロダクションコードを突発的に変更（ミューテーション）させてみてください。現実に起こり得る各ミューテーションに対して、少なくとも1つのテストが失敗するはずです：

- 定数や引数の誤り
- 誤ったブランチハンドラー
- 状態変更や副作用の欠落
- 空またはデフォルトの戻り値
- ゼロ、空、nil、未権限、または不正形式の入力に対するバリデーション欠落

いかなるミューテーションも検知できない場合、その挙動は保護されていないか、テストが同義反復（トートロジー）になっています。

## クイックリファレンス

| このようなとき... | こうする |
|-------------|-----|
| テストを書くとき | 捕まえる「破壊」に名前をつける — 決定ではなくバグ |
| 期待値を構築するとき | 手動で導出する。テスト対象コードを絶対に使わない |
| スクリプトやドキュメントをテストするとき | 実行する / 利用者をプレッシャーテストする。テキストの grep は禁止 |
| 依存関係のテストをするとき | 相手の仕様ではなく、自コードの境界契約をテストする |
| モック要素をアサートしたくなったとき | 実コンポーネントをテストするか、モックを解除する |
| メソッドをモックしようとするとき | その副作用を理解する。遅い/外部レベルをモックする |
| モックのレスポンスを作るとき | 実際の構造を完全に模倣する |
| テスト専用のクリーンアップが必要なとき | テストユーティリティに置く |
| モックのセットアップが肥大化したとき | 実コンポーネントを用いた統合テストに切り替える |
| テストファイルを完了するとき | ミューテーションチェックを実行する |

## 警告サイン (Warning Signs)

- セットアップとアサーションが同じオブジェクトを共有し、等価性が保証されてしまっている
- パニック、クラッシュ、またはセレクターの欠落によってしかテストが失敗しない
- 意図的な変更のたびにテストが失敗し、偶発的な破壊では決して失敗しない
- 期待値がループ、ビルダー、またはヘルパーの裏に隠されている
- テストがソーステキストを grep している、または削除されたシンボルが削除されたままであることをアサートしている
- フレームワークしか残っていなくてもテストが依然としてパスしてしまう
- カバレッジのためだけに存在し、副作用も結果もチェックしていない
- アサーションが `*-mock` テスト ID をチェックしている、またはモックを削除すると失敗する
- メソッドがテストファイルからしか呼び出されていない
- モックのセットアップがテストの半分以上を占めている、またはなぜモックが必要か説明できない
- 「念のため」という理由でモックしている
