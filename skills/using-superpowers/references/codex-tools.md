# Codex ツールマッピング

スキルは「ファイルを読む」「サブエージェントを派遣する」などのアクションで手順を記述します。実際に使えるツールの一覧を確認し、古い表や他の環境の設定より現在のツール定義を優先してください。

| スキルが要求するアクション | Codex での対応 |
|---|---|
| ファイルを読む、作成・編集・削除する | ワークスペース内のファイル操作ツール。シェル経由の環境では `shell`（例: `cat`, `head`, `tail`）や `apply_patch` を使う |
| シェルコマンドを実行する | `shell`。Codex アプリ環境では `functions.exec` から `exec_command` を使う |
| ファイル内容・名前を検索する | `rg`、`rg --files` などをシェルで使う |
| URL の内容を取得する | 利用可能なブラウザまたは web ツール。シェルのみの環境では `curl` / `wget` |
| Web 検索を実行する | 利用可能な `web_search` または web ツール。Codex CLI では既定で有効で、対応する `config.toml` の `web_search` 設定により `live`、`cached`、`disabled` を選べる |
| スキルを呼び出す | Codex のネイティブなスキルロード機構を使う |
| サブエージェントを派遣する | `spawn_agent`。分離した文脈には `fork_turns: "none"` を指定する |
| 独立した子を並列派遣する | スキルが並列化を指示し、共有状態や順序依存がなければ、1回の応答で複数の `spawn_agent` を呼び出す |
| 子エージェントへ追加指示を送り、作業を再開する | `followup_task` |
| 子エージェントの状態を確認する | `list_agents` |
| 子エージェントの結果を待つ | `wait_agent`。イベントを待つ仕組みなので短いタイムアウトでポーリングしない |
| 子エージェントを中断する | `interrupt_agent` |
| todo を管理する | 現在の環境にタスク管理ツールがあればそれを使う。なければ計画のチェックリストと台帳を更新する |

`close_agent` は V1 セッションのみで利用できます。V2 にはありません。V2 では完了した子エージェントは、スロットが必要になると自動的に退避します。V1 ではレビュー完了後にレビュアーを閉じ、タスクレビューを通過した後に実装者を閉じます。

## 指示ファイル

スキルが「指示ファイル」と言う場合、Codex ではプロジェクトルートの `AGENTS.md` を指します。グローバルの `~/.codex/AGENTS.md` も読み込まれ、プロジェクトまたは `~/.codex/` 内の `AGENTS.override.md` があれば優先されます。Codex は `project_doc_max_bytes`（既定32 KiB）の範囲で、プロジェクトルートから作業ディレクトリまでの `AGENTS.md` を結合します。

## 個人スキルディレクトリ

ユーザーのスキルは `$CODEX_HOME/skills/`（既定 `~/.codex/skills/`）に置けます。Codex はクロスランタイムの `~/.agents/skills/`（Copilot CLI、Gemini CLI と共有）も読み込みます。両方にスキルがある場合はそれぞれ別のカタログとして扱われ、現在の Codex ドキュメントでは優先順位は定義されていません。各スキルは `name` と `description` を含む `SKILL.md` を持つディレクトリです。

## サブエージェント

マルチエージェント機能が無効で必要なツールが表示されない場合、バージョンに応じて Codex 設定の `[features] multi_agent = true` を有効にします。機能名や利用可能なモデルはバージョンで変わるため、実際のツール一覧と派遣可能モデル一覧を確認してください。

- `spawn_agent` は既定で会話履歴全体を複製する場合があります。コンテキスト衛生のため、独立した派遣では `fork_turns: "none"` を使います。
- モデルを指定する場合は `model` と `reasoning_effort` の両方を明示します。名前をスキルや過去の会話から流用せず、現在の派遣可能一覧を確認してください。
- 修正ラウンドでは、元の実装者に `followup_task` で指示を送り再開します。新しい派遣を使うのは、元の子に継続指示を送れない場合など、スキルが定める条件に限ります。
- `wait_agent` はイベント通知を待ちます。手元に作業がある間は作業を続け、待機が必要なら `timeout_ms` を300000〜600000（5〜10分）にします。短いタイムアウトを連続させません。完了通知のあと `list_agents` で状態を確認し、完了したのに報告がない子があれば対応します。

Codex CLI の古い `rust-v0.115.0` より前のビルドでは、子エージェントの待機に `wait` を使っていました。現在の環境では `wait_agent` を使います。コード実行セルを再開する `functions.exec` の `wait` とは別の操作です。

機械レベルの既定値でモデル選択を明示したい場合、現在の Codex バージョンがサポートする設定を確認し、必要なら次のような設定を人間パートナーに提案します。

```toml
[features]
multi_agent = true

[agents]
default_subagent_model = "<派遣可能な中位モデル>"
default_subagent_reasoning_effort = "medium"
```

これらの設定項目は Codex のバージョンにより異なる場合があるため、導入前に現行設定仕様で有効性を確認します。

## 環境検出

ワークツリーを作成したりブランチを完了したりするスキルは、処理前に読み取り専用の Git コマンドで環境を確認します。

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

- `GIT_DIR != GIT_COMMON` は既にリンクされたワークツリー内であることを示します（ワークツリー作成をスキップ）。
- `BRANCH` が空なら detached HEAD です（その環境からブランチ作成、push、PR を行えません）。

詳細は `using-git-worktrees` の Step 0 と `finishing-a-development-branch` の Step 1 を参照してください。

## Codex アプリでの完了処理

外部管理されたワークツリーの detached HEAD などでサンドボックスがブランチや push 操作を妨げる場合、作業をコミットしたうえでアプリのネイティブ操作を案内します。

- **Create branch** — アプリ UI でブランチ名を指定し、コミット・push・PR を行う。
- **Hand off to local** — ユーザーのローカルチェックアウトへ作業を移す。

環境が許す範囲で、テスト実行、ステージング、推奨ブランチ名、コミットメッセージ、PR 説明の作成は引き続き行えます。
