# 計画の作成 (Writing Plans)

## 概要

エンジニアがこのコードベースもこの仕様も見たことがないことを前提に、実装計画を作成します。正確なインターフェースと正確なテストさえ分かればプロジェクトの言語で慣用的なコードを書け、計画が選択肢を残した箇所では合理的な判断ができる開発者だと仮定します。彼らが知り得ないのは、あなたが決めたことです。どのファイルか、どの名前とシグネチャか、仕様のどの値をどう使うか、各タスクをどのテストが証明するか。それらを記述します。計画は一口サイズのタスクに分割して提供されます。DRY（Don't Repeat Yourself）、YAGNI（You Aren't Gonna Need It）、TDD（Test-Driven Development）の原則に従い、頻繁なコミットを推奨します。

**開始時の宣言:** 「実装計画を作成するために writing-plans スキルを使用します。」

**コンテキスト:** 隔離されたワークツリーで作業する場合、そのワークツリーは実行時に `superpowers:using-git-worktrees` スキルを介して作成されている必要があります。

**計画の保存先:** `docs/plans/YYYY-MM-DD-<feature-name>.md`
- (計画の場所に関するユーザー設定がある場合は、そちらを優先します)

## 範囲チェック (Scope Check)

仕様書が複数の独立したサブシステムにわたっている場合は、brainstorming の段階でサブプロジェクトの仕様に分割されているべきです。そうなっていない場合は、サブシステムごとに個別の計画を立てることを提案してください。各計画は、それ自体で動作し、テスト可能なソフトウェアを生成する必要があります。

## ファイル構成 (File Structure)

タスクを定義する前に、どのファイルを作成または変更し、それぞれが何を担当するかを計画します。ここで設計上の決定が確定されます。

- 境界が明確で、定義されたインターフェースを持つ設計単位にします。各ファイルには1つの明確な責任を持たせます。
- 一度にコンテキストに保持できるコードについては、より正確に推論できます。ファイルが焦点を絞っているとき、修正はより信頼性が高くなります。機能が多すぎる大規模なファイルよりも、小さく焦点を絞ったファイルを優先してください。
- 共に変更されるファイルは共に配置されるべきです。技術的なレイヤーではなく、責任ごとに分割します。
- 既存のコードベースでは、確立されたパターンに従います。コードベースで大規模なファイルが使用されている場合は、一方的に再構成しないでください。ただし、変更しようとしているファイルが手に負えないほど大きくなっている場合は、計画の中で分割を検討するのが妥当です。

このファイル構成が、タスク分解の直接的な指針となります。**各タスクは、独立して意味を成し、それ自体が検証可能な「自己完結型」の変更を生成しなければなりません。**

## タスクの適切なサイズ設定 (Task Right-Sizing)

タスクとは、独自のテストサイクルを持ち、新たなレビュアーの承認ゲートを通す価値がある最小の単位です。タスクの境界を決定する際は、セットアップ、設定、足場作り（scaffolding）、およびドキュメント作成のステップを、それらの成果物を必要とする実際のタスクの中に折り込んでください。レビュアーが隣接するタスクを承認しながら、一方のタスクを有意義に却下できる場合にのみタスクを分割します。各タスクは、独立してテスト可能な成果物で終わる必要があります。

## 計画文書ヘッダー (Plan Document Header)

すべての計画文書は、以下のヘッダーから開始する必要があります。

```markdown
# [機能名] 実装計画

> **AIエージェントへの指示:** REQUIRED SUB-SKILL: この計画をタスクごとに実装するには、移植された `subagent-driven-development` スキル（推奨）または `executing-plans` スキルを起動して使用してください。ステップには追跡用のチェックボックス (`- [ ]`) を使用します。

**目標:** [この計画で構築する内容を説明する一文]

**アーキテクチャ:** [アプローチに関する2-3文]

**技術スタック:** [主要な技術/ライブラリ]

**仕様 (Spec):** [この計画が実装する仕様書/設計ドキュメントへのパス — 計画は仕様から議論されるため、仕様は計画と共に移動する。実行者は両方を読む]

**グローバル制約 (Global Constraints):**
- [仕様書に記載されているプロジェクト全体の要件（最低バージョン、依存関係の制限、命名や文言のルール、プラットフォームの要件など）を、仕様書からそのまま正確にコピーして1行ずつ記述します。すべてのタスクの要件には、暗黙的にこのセクションが含まれます。]

## レビューフォーカス (Review Focus)

[仕様が示唆しているが、どのタスクのテストも行使していない入力クラスや失敗モードのうち、このソフトウェアを使う人物に最も害を及ぼしそうなものを5件 — 入力や条件と、合理的な人物が期待する挙動を1行ずつ、可能性の高い順に。仕様書はビジョンドキュメントです。ソフトウェアが何をしなければならないかを記すものであり、出会うすべてを記すものではありません。ある入力への沈黙は、その入力でプログラムが壊れてよい許可ではありません。このリストはここに1度だけ、仕様書を前にして書きます。その後、各行に対応するテストを、そのコードを所有するタスクに、そのタスク固有のステップ形式で追加します。]

---
```

## ステップ粒度 (Step Granularity)

各ステップは1つのアクションと確認可能な結果にします。

- "失敗するテストを作成" - ステップ
- "テストが失敗することを確認するために実行" - ステップ
- "最小限の実装を作成" - ステップ
- "テストがパスすることを確認するために実行" - ステップ
- "コミット" - ステップ

## タスク構造 (Task Structure)

````markdown
### タスク N: [コンポーネント名]

**ファイル:**
- 作成: `exact/path/to/file.py`
- 変更: `exact/path/to/existing.py:123-145`
- テスト: `tests/exact/path/to/test.py`

**インターフェース (Interfaces):**
- 消費 (Consumes): [このタスクが以前のタスクから使用するもの — 正確なシグネチャ]
- 生産 (Produces): [後続のタスクが依存するもの — 正確な関数名、パラメータ、および戻り値の型。タスクの実装者は自身のタスクしか見ないため、このブロックで隣接するタスクが使用する名前や型を把握します。]

- [ ] **ステップ 1: 失敗するテストを作成**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **ステップ 2: テストが失敗することを確認するために実行**

実行: `pytest tests/path/test.py::test_name -v`
期待値: "function not defined"でFAIL

- [ ] **ステップ 3: `exact/path/to/file.py` に `function(input: InputType) -> ResultType` を実装**

シグネチャとテストだけでは選択肢が残る場合（どのライブラリ呼び出しか、どのデータ構造か）にアプローチを1行で記します。コードブロックは、それらでは決定できないアルゴリズムの場合にのみ記述します。

- [ ] **ステップ 4: テストがパスすることを確認するために実行**

実行: `pytest tests/path/test.py::test_name -v`
期待値: PASS

- [ ] **ステップ 5: コミット**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## ステップの内容 (What a Step Contains)

ステップは、それを読んだ実装者がちょうど1つの合理的なものを書ける状態になったときに完了です。それが要件のすべてです。曖昧さがなく、完全である必要はありません。各種類のステップは、それを曖昧さのないものにするために必要なものを運び、それ以上は運びません。

- **テストステップ:** テスト名とそのアサーションをコードとして、仕様書の正確な値を含めて記述します。
- **コードステップ:** 正確なシグネチャ（名前、パラメータ、戻り値の型）、それが存在するファイル、仕様が固定する具体的な値を記述します。本体は実装者が書きます。本体を記述するのは、シグネチャとテストでは決定できないアルゴリズムの場合、または仕様が固定する正確な文言の場合のみです。
- **検証ステップ:** 実行するコマンドと、パスを意味する出力を記述します。
- **他のタスクへの参照:** そのタスクの Interfaces ブロックが何を使うかを示します。計画はそのタスクのコードを繰り返しません。

計画とは、実装者が独力では決定できない決定の集合です。記述するコードより長い計画は、計画ではなくプログラムの書き写しです。何も決定しない行（"TBD"、「エッジケースを処理」、「適切な検証を追加」、「上記のテストを作成」、どのタスクも定義していない型や関数）は逆の失敗であり、セルフレビューで両方を検出します。


## セルフレビュー (Self-Review)

計画全体を書き終えた後、新鮮な目で仕様書を見直し、以下のチェックリストを**自分自身で**実行してください。これはサブエージェントのディスパッチ前に行う「自己防衛」です。

1. **仕様の網羅性**: 仕様書の各要件に対し、それを実装するタスクを特定できるか？
2. **ステップのスキャン**: すべてのステップが、実装者にちょうど1つの合理的なものを書かせるものになっているか、そしてどのステップもそれ以上を運んでいないか。何も決定しない行はギャップであり、シグネチャとテストで既に決定する関数本体は書き写しである。両方を修正する。
3. **型の整合性**: 後のタスクで使用する型、メソッド名、プロパティ名が、以前のタスクで定義したものと一致しているか？（例：タスク3で `clearLayers()`、タスク7で `clearFullLayers()` と呼ぶのはバグ）。
4. **レビューフォーカス**: 仕様が示唆する入力クラスや失敗モードごとに、それを行使するテストを持つタスクがあるか？ カバーされていないもののうち人物に害を及ぼしそうな上位5件をレビューフォーカスに記載し、各行のテストを所有タスクに追加する。空セクションは、チェックして何もなかったことを意味し、チェックを省略したことではない。
5. **分量**: 計画の長さを仕様の長さと比較する。実装する仕様の数倍も長い計画は、計画ではなくプログラムの書き写しである。コードブロックが文書の大半を占める場合は、本体をシグネチャに置き換え、テスト名とアサーションを確認し、各ステップが依然として曖昧さのないものか確認する。
6. **コマンドの正確性**: 記述したコマンドがそのディレクトリで実際に動作するか？

問題が見つかった場合は、その場で修正してください。再レビューは不要です。

## 実行の引き渡し (Execution Handoff)

計画を保存しセルフレビューした後、人間パートナーが読めるようリンクします。実行方法が既に明示されている場合は、計画をレビューして意図通りか確認してもらい、そのレビューを待ってから実装に進み、指定された方法を使います。そうでない場合は、計画のレビューと実行方法の選択を実装前に求めます。

**実行方法がまだ指定されていない場合:**

**「計画が完成し、`docs/plans/<filename>.md` に保存されました。計画をレビューしてください。どちらの実行アプローチを希望しますか？**

- **サブエージェント駆動** - タスクごとに新しいサブエージェントが実装し、新しいレビュアーが次のタスク開始前にチェックし、最後にブランチ全体のレビューを行います。最も徹底的。タスクごと・レビューごとに新しいコンテキストのコストがかかります。
- **ネイティブ** - このセッションで私自身が全タスクを実装します（このハーネスが作業を実行する方法そのまま）。ミッドティアのセッションモデルでも、計画が設計を運ぶため十分に動作します。最も安価で高速。独立したレビューは最後までありません。

**この計画には <どちらか> を推奨します。理由は <計画から引き出した1文: タスク間のインターフェース依存の度合い、タスク数、出荷時のミスのコスト> です。計画は意図通りでしょうか、どちらのアプローチで進めますか？」**

**実行方法が既に指定されている場合:**

**「計画が完成し、`docs/plans/<filename>.md` に保存されました。計画をレビューしてください。意図通りでしょうか？」**

**サブエージェント駆動が選択された場合:**
- **必須サブスキル:** `subagent-driven-development` を使用します。

**ネイティブが選択された場合:**
- **必須サブスキル:** `executing-plans` を使用します。
